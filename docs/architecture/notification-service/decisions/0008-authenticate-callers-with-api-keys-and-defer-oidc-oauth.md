## Context

Three kinds of caller reach the platform over HTTP: integrations (every one treated as a backend service, D-14), administrators using the administrative endpoints (D-06, D-12), and platform applications calling each other (today the API / Gateway calling the Delivery-status app's status query interface, D-56). Each needs a credential mechanism that identifies the caller and supports revocation.

The owner first set an OIDC/OAuth 2.0 direction (D-02, C-11) and an integration direction of OAuth 2.0 client credentials or API keys (D-28, C-34). Later reviews added one credential type per integration (D-31, C-37) and a revocation bound (D-32, C-38). No identity provider (IdP) has been selected, and none is planned for now (D-47, C-53). That left the IdP-dependent parts of the earlier decisions without anything to run on (HLD [§12](../high-level-design.md#12-inconsistencies-and-missing-information) I-22). The owner then defined the interim mechanisms for each caller type (D-50 to D-53) and the handling rules for API keys (D-64).

Relevant constraints: credentials and sensitive values never appear in logs, traces, or metrics (C-09). Clients' credentials grant access to the platform only, never to providers (C-14, D-04). Secrets are kept in a secrets store and may reach applications as environment variables (D-46, D-59).

## Decision

Canonical wording, from [context §8](../architecture-context.md#8-confirmed-decisions):

- **D-02:** "Identity and access: OpenID Connect (OIDC) for user identity, OAuth 2.0 for delegated access and service-to-service access, NestJS guards for enforcement. The identity provider is not yet selected."
- **D-28:** "Integration authentication, initial direction: OAuth 2.0 client credentials or API keys, depending on client requirements. Tenant identity is tied to credentials verified by the backend, never trusted from a client-supplied tenantId alone. The maximum revocation propagation time must be explicit, using a common community value. If JWTs are used, short lifetimes and the cost of revocation checks must be evaluated."
- **D-31:** "Each integration has exactly one credential type, OAuth 2.0 client credentials or an API key, chosen by an administrator when the integration is created. Never both."
- **D-32:** "Revocation takes effect within 5 minutes at most: revocation happens in the integration registry, the registry cache lasts 60 s or less, and JWT access tokens last 5 minutes."
- **D-47:** "No identity provider for now. Integrations authenticate with platform-issued API keys ("API key/token"). The IdP-dependent parts of D-02, D-28, D-31, and D-32 are deferred until an IdP is introduced."
- **D-50:** "Delegated access (a system acting on behalf of a person) is not needed for now."
- **D-51:** "'API key' and 'token' mean the same thing: one platform-issued secret per integration, sent in a request header."
- **D-52:** "Administrators authenticate with administrator API keys that are valid only on the administrative endpoints, never on integration traffic."
- **D-53:** "Internal service-to-service calls (for example API → delivery-status application) authenticate with a service key per calling application, injected through environment variables, plus a network restriction."
- **D-64:** "API keys (integration and administrator) are generated by the platform and shown once, stored only as peppered hashes, sent only in request headers, scoped to one integration or to the administrative surface, rotated with a short overlap period, and never logged; a non-secret prefix identifies them."

**Net interim position (D-47, D-50 to D-53, D-64):**

| Caller | Now | Deferred target (until an IdP exists) |
|---|---|---|
| Integration | Platform-issued integration API key, one per integration (D-51). Under D-31, every integration currently has the API-key credential type (C-37). | OAuth 2.0 client credentials as the alternative credential type (D-28, D-31). |
| Administrator | Administrator API key, valid only on the administrative surface (D-52). | OIDC sign-in (D-02). |
| Platform application → platform application | Service key per calling application, delivered through environment variables, plus a network restriction (D-53). | OAuth 2.0 service-to-service access (D-02). |

Parts that stay in force now: enforcement in NestJS guards (D-02); the tenant comes only from credentials verified by the backend (D-28); one credential type per integration, never both (D-31); revocation in the integration registry with a cache of 60 s or less (D-32), so a revoked key stops working within about a minute. The 5-minute JWT lifetime (D-32) applies only once an IdP exists. Delegated access is not needed (D-50).

**Revisit trigger:** introducing an IdP. That is a new owner decision (README §3.3), which would refine or supersede this ADR for the deferred parts.

**Resolved inconsistencies recorded here, as HLD §12 asks:**

- **I-21:** D-02 and D-05 describe integrations in OAuth terms, while D-28 also allows API keys. D-31 resolves it: D-05 reads as "one credential per integration", either an OAuth client or an API key, never both.
- **I-22:** D-47 suspends the IdP-dependent parts of D-02, D-28, D-31, and D-32. Those parts are the deferred target design (HLD §8.1), recorded in the table above.

## Alternatives considered

- **OAuth 2.0 client credentials for integrations now** (one of the two options in D-28): deferred, not rejected. No IdP exists to issue the tokens (D-47). (Source: HLD §8.1, §10 "API keys only, no IdP for now".)
- **OIDC for administrators and OAuth 2.0 between applications now** (D-02): deferred for the same reason; interim static keys are used instead (D-52, D-53). (Source: HLD §8.1, §10.)
- **An integration holding both credential types:** rejected by D-31 ("Never both"). Changing type means issuing the new credential and revoking the old one. (Source: HLD §8.1, review revision 11.)
- **Token introspection with the IdP on every request:** Rejected. It adds an IdP round-trip to every call, while the registry check already gives faster revocation. (Source: HLD §8.1, revocation propagation.)
- **Delegated access (a system acting on behalf of a person):** not needed for now (D-50). (Source: HLD §11, OQ-25.)
- The specific values in D-32 (5 minutes overall, 60 s cache) were chosen from the "commonly used range" of 5–15 minutes. No other value was recorded as considered.
- For D-51 and D-64: not recorded when the decision was made.

## Consequences

- **Positive:** nothing extra to run or integrate, and the scheme is simple for integrations (HLD §10). Revocation through the registry takes effect within about a minute, faster than the 5-minute bound. Every credential type resolves to the same integration record, so tenant resolution and everything after it does not depend on the mechanism (HLD §8.1).
- **Negative / accepted risks:**
  - API keys, administrator keys, and service keys are long-lived static secrets. Leaks are more likely than with short-lived tokens. The mitigations are revocation, rate limits (D-36, ADR-0009), and rotation (HLD §8.1, §10).
  - The integration registry is on every request's path (cached for 60 s or less).
  - Rotating a service key delivered through environment variables needs a coordinated redeploy of both sides (HLD §8.1, §8.2).
  - **Credentials placed in frontends.** D-14 (recorded in ADR-0009) does not make this risk moot. It is what makes it an accepted risk: the platform treats every integration as a backend and designs no controls for credentials on end-user devices. If a tenant puts an integration API key in a frontend, the key is exposed. The platform treats it as that tenant's leaked credential: rate limits contain it, and revocation through the registry removes it (HLD §8.1 "Accepted risk (D-14)", §10). QS-12 (frontend abuse containment) was retired for this reason.
- **Follow-up:**
  - An IdP selection (no OQ-nn tracks it; HLD §2.3 notes "IdP product still open" against D-28) triggers a revisit of the deferred parts.
  - The **Proposed** items in HLD §8.1 stay proposals and are not decided by this ADR: the per-caller enforcement table, the shared auth library, the starting scope set, the example 24-hour rotation overlap, and API keys issued through the administrative endpoints.
  - The identity and access design note and the HTTP API contracts (HLD §13 items 5 and 6) need to describe the API-key security schemes in use now.
